# 劳动链的政治经济学本体

本文整理当前 LabourChain 关于劳动、劳动成果、仓库与项目的理论基线，用于后续需求、Spec、实现和产品设计的长期对照。

它不是某个具体功能的需求清单，也不是工程 Spec。`docs/requirements.md` 仍然是 Repository 产品需求的唯一事实来源；当需求、Spec 或实现与本文的基本概念发生冲突时，应显式回到理论与产品层讨论，而不是在代码中静默选择一种解释。

## 核心命题

LabourChain 试图建立劳动过程的数字孪生。

大量现有系统已经能够记录文件、代码、数据、模型、作品等劳动成果，也就是已经对象化的劳动。LabourChain 同样记录这些成果，但更核心的目标是把**活劳动本身**作为第一等事实记录下来：谁进行了劳动、形成了什么劳动成果、这些劳动发生在什么组织与确证关系中。

因此，劳动链不仅记录死劳动，也试图建立活劳动的数字孪生。

## 劳动者：劳动主体

**Worker / Member = 劳动者 = 劳动主体。**

劳动者是 LabourChain 中唯一能够产生劳动记录、产生劳动成果的劳动主体。这是政治经济学劳动理论在 LabourChain 中的技术实践模型。

Repo、Project、Runtime、AI、Agent 等都可以参与劳动过程的组织、辅助、执行、存储或分析，但它们本身不是劳动主体，不能替代劳动者成为劳动记录和劳动成果的生产者。

## Record：劳动记录与活劳动

**Record = 劳动记录 = 活劳动的数字记录。**

劳动记录描述劳动者实际发生的劳动。它是链上的事实记录，不依赖某个 Repo 内部存在一个 `records` 容器才能成立。

劳动记录由劳动者产生，并从劳动者视角归属于劳动者。劳动者的劳动历史可以从链上所有与该劳动者相关的 Record 重新恢复和组织。

劳动并不必然产生一个新的 Asset。会议、沟通、组织、检查、学习、维护等劳动都可以形成 Record，即使没有形成一个独立的新劳动成果。

因此 Record 与 Asset 有关系，但 Record 不能被建模为 Asset 的附属字段。

## Asset：劳动成果与死劳动

**Asset = 劳动成果 = 已对象化的劳动 = 死劳动。**

Asset 是劳动者通过劳动形成、修改或维护的劳动成果。代码、文档、模型、数据、设计、构建产物，以及现实劳动成果的数字表示，都可以成为 Asset。

Asset 与 Record 一样具有链上的规范表示，但二者表达的是不同性质的事实：Record 记录活劳动，Asset 表示劳动已经对象化之后形成的成果。

## Repo：仓库

**Repo = 仓库。**

仓库的中心对象是 Asset，也就是死劳动。Repo 存放劳动成果，并在劳动者向仓库提交劳动成果时参与对相关劳动记录的确证。

Repo 不需要拥有一个规范性的 `records[]` 字段。与 Repo 有关的劳动历史来自链上的 Record 关系，可以从 Repo 视角重新构建。

实际运行中，Repository、Board、Flow 等服务可以缓存、索引链上的 Record，以避免每次日常分析都从链重新构建完整视图。这些缓存属于运行时投影，不是规范事实本身。

### 劳动者视角与仓库视角

同一条劳动记录可以同时具有两个重要视角：

- 劳动者视角：这是谁进行的劳动；
- 仓库视角：这次劳动是否作为某个仓库的 contribution 被接收和确证。

Repo 对劳动的确证并不把劳动记录从劳动者转移给仓库。劳动者仍然可以从自己的视角恢复劳动历史；Repo 也可以从自己的视角恢复 contribution history。

这与 Git / GitHub 的使用经验相似：仓库可以看到 commit 与 contributors，个人也可以看到自己的 commit / contribution 历史，但劳动记录在 LabourChain 中被提升为独立的链上事实，而不只是 commit message 的附属信息。

## Asset contribution 与 Record

在 Repo contribution 场景中，劳动者提交的是 Asset。

这次提交同时伴随描述该劳动过程的 Record。Repo 接受 Asset 时，对相关劳动关系形成仓库侧确证，并可以在运行时缓存这些 Record，用于构建仓库历史、劳动链与后续分析。

因此，Repo contribution 可以被理解为：

```text
劳动者进行劳动
    ↓
形成 / 修改劳动成果 Asset
    ↓
产生劳动记录 Record
    ↓
向 Repo 提交 Asset
    ↓
Repo 接收 Asset，并确证相关劳动记录
```

但这一流程只描述 Repo contribution。它不意味着所有 Record 都必须依附 Asset，也不意味着劳动者必须先加入某个公共 Repo 才能产生劳动记录。

## Personal Repo：劳动者的私人劳动成果仓库

劳动者可以建立 Repo，任何劳动者理论上都可以像建立 Git 仓库一样建立自己的仓库。

每个劳动者可以默认拥有一个 Personal Repo，用于存放尚未进入公开 Repo 的私人 Asset，例如个人数据、健康资料、使用偏好、未公开材料等。

Personal Repo 不是劳动记录仓库。劳动者拥有的 Record 仍然作为链上劳动事实存在，不需要在 Personal Repo 中维护一个额外的记录集合。

Personal Repo 的主要意义是保存和管理劳动者自己生产、但尚未公开或尚未交由公共组织调度的死劳动。

## Project：劳动组织形式

**Project = 项目 = 对劳动者、活劳动与死劳动的一种组织形式。**

Project 组织的是：

```text
劳动者
+ 活劳动（Record）
+ 死劳动（Asset）
```

Project 不等于 Repo，也不是 Repo 的目录。一个 Project 可以组织来自不同 Repo、Personal Repo 授权以及其他合法来源的 Record 与 Asset。

从政治经济学角度看，Project 关心的不是“资料存在哪里”，而是哪些劳动者围绕什么目标，使用哪些既有劳动成果，投入哪些新的活劳动，并形成哪些新的劳动成果。

## 私人、公开与公共

当前阶段可以把 Personal Repo 理解为唯一的 Private Repo。其他 Repo 一旦发布到链上，遵循“上链即公开”的原则。

公开与公共描述的是使用关系，而不是作者是否存在：

- **公开**：Asset 可以被读取或使用，但读取 / 使用需要留下具名、可追踪的使用关系；
- **公共**：Asset 允许无记名使用或再生产使用，不要求每次使用都形成具名记录。

无记名使用不等于没有生产者或来源。Asset 的生产者与 provenance 仍然存在，只是不要求每次 use 都建立具名使用关系。

## 有痕授权与数据使用

劳动者可以通过 Flow 等插件，把 Personal Repo 中的私人 Asset 授权给 Project 或 Repo 使用，并让授权与使用过程留下记录。

对于大量劳动者共同管理同类数据的场景，可以建立专门 Repo 统一调度。例如健康管理追踪仓库可以接收劳动者授权的数据，使用者通过该 Repo 获取和使用这些 Asset，而不必逐个重新向劳动者请求授权。

这也为未来“读取和使用劳动者生产的数据，应当让数据生产者获得收益”留下技术基础：首先记录生产者、使用者、被使用的劳动成果和使用关系，再在其上建立后续的核算与分配机制。

当前理论基线不规定具体收益算法、代币机制或分配比例。

## 软件资产的使用与 contribution

以 LabourFlow 为例，项目可以同时发布源码 Asset 与构建后的插件 Asset。

普通使用者不需要 clone 仓库，可以通过 CI、包分发或 Runtime 直接获得构建后的插件并使用。

只有当使用者希望参与开发劳动时，才通常进入 clone、fork、修改、提交等 contribution 流程，并由新的劳动形成新的 Record 与 Asset。

因此“使用一个软件劳动成果”和“参与该软件的生产劳动”是不同关系，不应简单用 clone 行为代表软件使用。

## 隐私与未来的零知识证明

“上链即公开”是当前普通 Repo 的基本原则，但这不意味着未来所有链上 Asset 都必须公开明文内容。

未来可以通过零知识证明、承诺或其他密码学机制，使链上能够证明某个 Asset、劳动记录及其关系真实存在，而无需公开 Asset 的具体内容。这可以成为未来 Private Repo 的基础。

当前阶段不实现这一能力，只保留理论上的兼容性：Personal Repo 是当前唯一的私人仓库，其他发布到链上的 Repo 默认公开。

## Git 仓库类比

LabourChain 与 Git 的结构存在一个有帮助但并不完全等同的类比：

```text
Git / GitHub                     LabourChain
------------------------------------------------------
仓库中的内容                     Asset / 劳动成果 / 死劳动
commit 中的劳动描述              Record / 劳动记录 / 活劳动
repository history              Repo 视角的 contribution history
personal commits/contributions  Worker 视角的 labour history
```

区别在于 LabourChain 将劳动者、活劳动、死劳动、仓库确证和项目组织关系显式建模，而不是让劳动关系隐含在代码提交历史中。

## 理论基线

目前可以把 LabourChain 的基础本体压缩为：

> 劳动者是劳动主体；劳动记录是活劳动的数字孪生；劳动成果是活劳动对象化形成的死劳动；仓库存放劳动成果并参与劳动确证；项目则组织劳动者、活劳动与死劳动。

后续需求、协议、产品与实现应持续与这一基线对照。需要偏离时，应先明确这是理论模型的修订、产品层的特殊要求，还是仅仅运行时的技术投影。
